3 ОПИС ВИКОНАНОЇ РОБОТИ
3.1 Обрана мова програмування та її особливості
Для аналізу обрано мову програмування C. Її створив Денніс Рітчі в Bell Labs на початку 1970-х років для розробки операційної системи UNIX [1]. C - процедурна мова зі статичною типізацією, стандартизована ISO; актуальні редакції стандарту - C11, C17 і C23. Мовою C написано ядро Linux, драйвери пристроїв, вбудоване програмне забезпечення мікроконтролерів, СУБД SQLite та інтерпретатор CPython.
Особливості мови, які безпосередньо впливають на правила оформлення коду:
– ручне керування пам’яттю і робота з вказівниками: помилка призводить до витоку пам’яті або невизначеної поведінки;
– відсутність просторів імен, класів і винятків: модульність досягається поділом коду на файли .h і .c, а про помилки повідомляють кодами повернення;
– препроцесор, який підставляє текст до компіляції і не перевіряє типи;
– мінімальні перевірки під час виконання: вихід за межі масиву чи робота з NULL не виявляються автоматично.
Через ці особливості в C особливо важливо, щоб код був охайним, однаково оформленим і перевіреним інструментами: це зменшує кількість помилок, які складно знайти під час виконання програми.

3.3 Рекомендація 1. Осмислені імена та префікс модуля
Рекомендація: використовуйте осмислені назви змінних і функцій та додавайте до назв функцій префікс модуля.
Опис: змінні й функції записують малими літерами з підкресленням між словами, константи й макроси - великими літерами, типи - з великої літери. Назва функції описує дію (parse_line()), функція-перевірка формулюється як питання (is_empty()). Однолітерні імена допустимі лише для лічильників коротких циклів. Суфікс _t у власних типах не використовують, оскільки стандарт POSIX резервує його для системних типів.
Чому це важливо для C: у мові немає просторів імен і класів, тому всі функції програми знаходяться в одному глобальному просторі. Префікс модуля запобігає конфліктам імен і одразу показує, до якого файлу належить функція [1, 2].
Наслідки недотримання: короткі імена на кшталт chk чи snd доводиться розшифровувати, читаючи реалізацію, а однакові імена в різних модулях спричиняють помилки компонування.
Вплив на підтримку коду: зрозумілі імена скорочують час на читання та рев’ю коду, полегшують пошук функцій у проєкті й зменшують потребу в коментарях.
Приклад (рисунок Б.2):
Поганий приклад:
 1  int chk(int t);
 2  void snd(char *b, int l);
Гарний приклад:
 1  TempLevel sensor_check_temp(int temp_c);
 2  void uart_send(const char *buffer, size_t length);
3.4 Рекомендація 2. Іменовані константи замість «магічних чисел»
Рекомендація: замінюйте «магічні числа» іменованими константами або переліченнями.
Опис: числові значення, зміст яких не очевидний з контексту (пороги, розміри буферів, коди результатів), виносять у макроси #define, константи const або перелічення enum з осмисленими назвами.
Чому це важливо для C: функції в C часто повертають числові коди стану, і без перелічення неможливо зрозуміти, що означає 1 чи 2. Перелічення enum також дає компілятору змогу попередити про пропущений варіант у switch.
Наслідки недотримання: щоб змінити поріг, доводиться шукати всі місця з однаковим числом; пропущене місце стає прихованою помилкою.
Вплив на підтримку коду: значення змінюється в одному місці, а код читається без додаткових коментарів.
Приклад (рисунок Б.2, додаток В, підрозділи В.1–В.3):
Поганий приклад:
 1  if (t > 85) {
 2      return 2;
 3  }
Гарний приклад:
 1  #define TEMP_CRITICAL_C 85
 2  
 3  if (temp_c > TEMP_CRITICAL_C) {
 4      return TEMP_CRITICAL;
 5  }
3.5 Рекомендація 3. Однакові відступи та фігурні дужки завжди
Рекомендація: форматуйте код однаково та завжди ставте фігурні дужки навколо тіла умов і циклів.
Опис: відступ - 4 пробіли (у стилі ядра Linux - табуляція шириною 8 [5]), довжина рядка - до 80–100 символів. Дужку функції ставлять з нового рядка, а в if, for, while - у тому ж рядку [1]. Пробіли ставлять після ключових слів і навколо операторів, логічні блоки розділяють порожнім рядком.
Чому це важливо для C: синтаксис C дозволяє записувати тіло умови без дужок, і тоді умові належить лише перший оператор незалежно від відступів.
Наслідки недотримання: оманливі відступи приховують логічні помилки. GCC з прапорцем ‑Wall виявляє частину таких випадків, але не всі.
Вплив на підтримку коду: однаковий стиль робить зміни в Git чистішими, а новий рядок, доданий до умови, не змінює логіку випадково.
Приклад (рисунок Б.3):
Поганий приклад:
 1  if (len > MAX)
 2      len = MAX;
 3      truncated = true; // виконується завжди
Гарний приклад:
 1  if (len > MAX) {
 2      len = MAX;
 3      truncated = true;
 4  }
3.6 Рекомендація 4. Кожен вказівник в окремому оголошенні
Рекомендація: оголошуйте кожну змінну в окремому рядку, а зірочку вказівника пишіть біля імені змінної.
Опис: запис char *name відповідає тому, як C розбирає оголошення: зірочка належить до імені, а не до типу.
Чому це важливо для C: в оголошенні int* begin, end; вказівником є лише begin, а end має тип int. Запис зірочки біля типу створює хибне враження, що обидві змінні - вказівники.
Наслідки недотримання: помилка проявляється далеко від оголошення - під час присвоєння адреси чи розіменування, - і її складно помітити на рев’ю.
Вплив на підтримку коду: одне оголошення в рядку простіше коментувати, змінювати та видаляти, а diff у Git показує лише змінену змінну.
Приклад (рисунок Б.3):
Поганий приклад:
 1  int* begin, end;   // end — не вказівник
Гарний приклад:
 1  int *begin;
 2  int *end;
3.7 Рекомендація 5. Коментарі пояснюють «чому», а не «що»
Рекомендація: пишіть коментарі, які пояснюють, чому код написано саме так, а не переказують, що він робить.
Опис: коментують неочевидні рішення, обмеження обладнання, протоколів або стандартних функцій. Очевидні коментарі та закоментований старий код видаляють, оскільки історію змін зберігає Git. Для коротких приміток використовують (//), для довших - ( /* */); позначки TODO і FIXME доповнюють номером задачі [2].
Чому це важливо для C: стандартна бібліотека C має функції з неочевидною поведінкою. Наприклад, strncpy не додає завершальний нуль-символ, якщо рядок-джерело довший за буфер; без пояснення рядок, що виправляє це, виглядає зайвим.
Наслідки недотримання: інший розробник може «спростити» код і видалити рядок, який захищає від виходу за межі буфера, а застарілі коментарі вводять в оману.
Вплив на підтримку коду: коментарі зберігають причини рішень, які інакше втрачаються разом з автором коду.
Приклад (рисунок Б.4, додаток В, підрозділ В.4.2):
Поганий приклад:
 1  count++;               // збільшуємо count
 2  /* len = strlen(name); */
Гарний приклад:
 1  /* strncpy не додає '\0', якщо src довший
 2     за буфер, тому завершуємо рядок вручну */
 3  strncpy(dst, src, size - 1);
 4  dst[size - 1] = '\0';
3.8 Рекомендація 6. Документування інтерфейсу за допомогою Doxygen
Рекомендація: документуйте публічний інтерфейс модуля коментарями Doxygen.
Опис: коментар починається з /** або /// і розміщується перед оголошенням функції в заголовковому файлі. Тег @brief містить короткий опис, @param - опис параметрів із напрямом [in], [out] або [in,out], @return і @retval - результат і коди помилок. Doxygen формує з цих коментарів довідку у форматі HTML або PDF [8]; налаштування зберігаються у файлі Doxyfile, який створює команда doxygen ‑g.
Чому це важливо для C: сигнатура функції не показує, чи може параметр бути NULL, хто звільняє пам’ять і чи змінює функція дані за вказівником. Позначки [in] і [out] відповідають саме на ці питання.
Наслідки недотримання: без документації користувач функції змушений читати її реалізацію або вгадувати контракт, що призводить до помилок роботи з пам’яттю.
Вплив на підтримку коду: документація генерується з коду й оновлюється разом із ним, тому не розходиться з реалізацією.
Приклад (рисунок Б.5, додаток В, підрозділ В.4.1):
Поганий приклад:
 1  int text_copy(char *dst, const char *src, size_t size);
Гарний приклад:
 1  /**
 2   * @brief Копіює рядок у буфер фіксованого розміру.
 3   *
 4   * @param[out] dst  Буфер призначення.
 5   * @param[in]  src  Рядок-джерело, не NULL.
 6   * @param[in]  size Розмір dst у байтах.
 7   *
 8   * @retval  0 Рядок скопійовано повністю.
 9   * @retval -1 Рядок обрізано або аргументи некоректні.
10   */
11  int text_copy(char *dst, const char *src, size_t size);
3.9 Рекомендація 7. Перевірка вхідних даних і коди помилок
Рекомендація: перевіряйте вхідні дані та повідомляйте про помилки через значення, що повертається.
Опис: функція перевіряє вказівники на NULL і розміри буферів до роботи з ними та повертає код результату, описаний у документації. Код, що викликає функцію, перевіряє цей результат.
Чому це важливо для C: у мові немає винятків, тому про помилку можна повідомити лише значенням, що повертається, або через змінну errno. Розіменування NULL і запис за межі буфера - невизначена поведінка; стандарт SEI CERT C містить окремі правила щодо цього, зокрема STR31-C (достатній розмір пам’яті для рядка) та ERR33-C (перевірка помилок функцій стандартної бібліотеки) [6].
Наслідки недотримання: аварійне завершення програми, пошкодження пам’яті та вразливості типу переповнення буфера.
Вплив на підтримку коду: помилка виявляється там, де виникла, а не в іншій частині програми, тому її простіше знайти та виправити.
Приклад (додаток В, підрозділ В.4.2):
Поганий приклад:
 1  void copy_name(char *dst, const char *src)
 2  {
 3      strcpy(dst, src); // розмір dst невідомий
 4  }
Гарний приклад:
 1  int text_copy(char *dst, const char *src, size_t size)
 2  {
 3      size_t len;
 4  
 5      if (dst == NULL || src == NULL || size == 0) {
 6          return -1;
 7      }
 8  
 9      len = strlen(src);
10  
11      /* strncpy не додає '\0', якщо src довший
12         за буфер, тому завершуємо рядок вручну */
13      strncpy(dst, src, size - 1);
14      dst[size - 1] = '\0';
15  
16      return (len < size) ? 0 : -1;
17  }
3.10 Рекомендація 8. Єдиний стандарт стилю та clang-format
Рекомендація: дотримуйтеся одного стандарту стилю в усьому проєкті та перевіряйте його автоматично.
Опис: для мови C немає єдиного офіційного стилю; найпоширеніші стандарти наведено в таблиці 3.1. Обраний стиль записують у файл .clang‑format у корені проєкту. Команда clang‑format ‑i виправляє форматування файлів, а режим ‑‑dry‑run ‑‑Werror лише перевіряє їх і повертає помилку в разі порушень [7].
Чому це важливо для C: у різних проєктах на C прийнято різні правила, тому без явно обраного стандарту кожен розробник форматує код по-своєму.
Наслідки недотримання: «шум» у diff, суперечки на рев’ю та конфлікти злиття через зміни відступів.
Вплив на підтримку коду: clang-format виправляє форматування автоматично, тож на рев’ю обговорюють лише логіку, а редактори (VS Code, CLion) підхоплюють файл .clang‑format без додаткових налаштувань.

	3.11 Рекомендація 9. Попередження компілятора та автоматичний аналіз
Рекомендація: вмикайте попередження компілятора, використовуйте статичний і динамічний аналіз та запускайте перевірки автоматично.
Опис: прапорці ‑Wall ‑Wextra вмикають попередження, а ‑Werror робить їх помилками. Статичні аналізатори cppcheck [9] і clang-tidy знаходять розіменування NULL, вихід за межі масиву та витоки пам’яті без запуску програми; AddressSanitizer і Valgrind виявляють помилки пам’яті під час виконання. Хук pre-commit і CI у GitHub Actions запускають перевірки для кожної зміни.
Чому це важливо для C: компілятор C за замовчуванням пропускає багато підозрілих конструкцій, а помилки пам’яті часто не проявляються одразу: програма працює «правильно» до певного моменту.
Наслідки недотримання: попередження накопичуються й ігноруються, а помилки потрапляють у робочу версію програми.
Вплив на підтримку коду: перевірки виконуються однаково для всіх розробників, і помилки виявляються ще до рев’ю.


3.12 Рекомендація 10. Модульні тести та розробка через тестування
Рекомендація: покривайте функції модульними тестами і пишіть тест раніше за код (TDD).
Опис: цикл TDD: написати тест, який не проходить, написати мінімальний код для його проходження, після чого покращити код, зберігши проходження тестів [4]. Для C використовують бібліотеки Unity [10], CMocka, Check. Тест складається з трьох кроків - підготовка даних (Arrange), виклик функції (Act) і перевірка результату (Assert), перевіряє одну поведінку і має назву, що цю поведінку описує. Залежності від часу, файлів або обладнання замінюють заглушками.
Чому це важливо для C: у мові немає вбудованих засобів тестування та перевірок під час виконання, тому помилки в граничних випадках (переповнення, порожній масив, NULL) виявляються лише тестами або аварією програми.
Наслідки недотримання: кожна зміна коду ризикує зламати вже працюючу поведінку, тому рефакторинґ стає небезпечним.
Вплив на підтримку коду: тести фіксують очікувану поведінку, тож код можна безпечно змінювати. У проєкті тести запускаються командою make test і в CI; усі тести проєкту (у звіті наведено один із них) виконуються успішно.
Приклад (рисунок Б.8, додаток В, підрозділ В.4.3):
Поганий приклад (перевірка «на око», без тесту):
 1  printf("%d\n", clamp(150, 0, 100));
Гарний приклад:
 1  void test_clamp_limits_value_to_max(void)
 2  {
 3      int value = 150;                    /* Arrange */
 4      int result = clamp(value, 0, 100);  /* Act */
 5      TEST_ASSERT_EQUAL_INT(100, result); /* Assert */
 6  }
3.13 Рекомендація 11. Рефакторинґ без зміни поведінки
Рекомендація: покращуйте структуру коду невеликими кроками, не змінюючи його поведінки, і застосовуйте наведені рекомендації разом.
Опис: рефакторинґ - це зміна внутрішньої структури коду без зміни його зовнішньої поведінки [3]. У прикладі функцію f перейменовано на sum_positive, параметр-масив позначено як const, для кількості елементів використано тип size_t, а для суми - int64_t; додано перевірку на NULL, Doxygen-коментар і форматування за правилами.
Чому це важливо для C: компактний код у стилі ранніх програм на C (усе в один рядок, однолітерні імена, без дужок) складно перевірити й безпечно змінити, а сума типу int може переповнитися, що в C є невизначеною поведінкою.
Наслідки недотримання: незрозумілий код бояться змінювати, тому помилки в ньому залишаються, а нові функції дублюють старі.
Вплив на підтримку коду: після рефакторинґу код компілюється з ‑Werror, відповідає правилам clang-format і читається без пояснень автора; поведінка функції не змінилася.
Приклад (рисунок Б.9, додаток В, підрозділи В.2, В.3):
Поганий приклад:
 1  int f(int*a,int n){int s=0,i;
 2  for(i=0;i<n;i++)if(a[i]>0)s+=a[i];return s;}
Гарний приклад:
 1  /** @brief Сума додатних елементів масиву. */
 2  int64_t sum_positive(const int *values, size_t count)
 3  {
 4      int64_t total = 0;
 5  
 6      if (values == NULL) {
 7          return 0;
 8      }
 9      for (size_t i = 0; i < count; i++) {
10          if (values[i] > 0) {
11              total += values[i];
12          }
13      }
14      return total;
15  }

 5  int text_copy(char *dst, const char *src, size_t size)
 6  {
 7      size_t len;
 8  
 9      if (dst == NULL || src == NULL || size == 0) {
10          return -1;
11      }
12  
13      len = strlen(src);
14  
15      /* strncpy не додає '\0', якщо src довший

21  }
